# 中测阶段发现的11个错误与交付未完成的原因分析

> [!abstract] 📌 本篇主题
> Hindsight 四库记忆体系宣布交付之后，本人在同日夜里做了一次「停服务 → 重启 → 数模板 → 逐库实测 → 对比交付标准」的独立验收，随后又执行了删数据与修启动。本篇如实记录：**最终测试阶段发现的每一个错误**（含偶发、轻微、被临时绕过的）、**测试为何没能拦住问题**，以及**对上一轮「草率标记已完成」的核查结论**。定性口吻遵照本人要求：不隐瞒、不淡化、不美化。
>
> 上游背景见 [[部署记忆大师]]、[[部署记忆大师2]]、[[Hindsight 四库记忆体系工作复盘 2026-10-22 至 2026-10-23]]。

---

## 一、背景：这次验收是怎么触发的

交付当时给出的结论是「可以交付，建议现在停」，依据是四份文档里的一组验收阈值表。本次验收的出发点是：把服务真正停掉、再按交付物自带的方式拉起来，看它是不是还能用。

执行顺序严格按本人要求：① 先关闭再重启 → ② 数 bank 模板并确认是否为 4 个 → ③ 对四个库逐一做「打开 + 写入 + 召回」实测 → ④ 与交付标准逐项对比，判断差距或超额。

结论先行：**第一步就炸了。**

## 二、终测阶段发现的错误（阶段①清单）

### 2.1 产品 / 交付本身的缺陷（3 条）

| # | 问题 | 现象 | 复现方式 | 处置 |
|---|---|---|---|---|
| A1 | **一键启动在干净环境下直接崩溃（P0）** | `ValueError: LLM API key is required. Set HINDSIGHT_API_LLM_API_KEY`，服务起不来 | 停掉服务后用「不含任何环境变量」的干净环境执行启动脚本，或裸跑 API 可执行文件 | 已修复：新建 `.env`（含 LLM provider / model / 数据库连接串等配置） |
| A2 | **单条事实无法按 id 删除** | `DELETE /banks/{库}/memories/{id}` 返回 **405**；openapi 中该路径只暴露 GET / PATCH | 对任意 memory_id 发 DELETE | 未修复，已找到替代路径：**删文档会级联删光其下全部事实** |
| A3 | **文档计数接口滞后** | 写入已成功，`/stats` 的 `total_documents` 仍显示旧值 | retain 后立刻比对 `/stats` 与 `/documents` | 未修复（属接口行为）。判定是否写入成功必须看 `/documents` 列表，否则会误判「没写进去」 |

补充一条连带发现：**上一轮自己写的《四库验收测试提示词-修正版》，本身并未被验证过**——它第 B.8 节写的「逐条 DELETE /memories/{id} 清理」在本版本上根本不可用。

### 2.2 我的操作与验证失误（6 条，均已纠正）

| # | 问题 | 现象 | 后果 |
|---|---|---|---|
| B1 | 接口探测被代理拦截产生假阳性 | 停掉服务后 `curl` 仍显示「有响应」（实为代理返回的 502） | 差点得出「停止失败」的错误结论；改用 socket 直连才确认已停 |
| B2 | 未先查接口定义就写测试脚本 | 拿 `GET /banks/{id}` 当「打开」接口，四个库全被判 FAIL | 一度误报「四个库都打不开」——是我用法错，不是库有问题 |
| B3 | 清理时差点漏删衍生事实 | 只盯 `document_id` 匹配的条目，漏了若干条由模型二次抽取产生、`document_id` 为空的派生事实 | 若按第一版清单删，**正式库会残留测试垃圾**；最终按全量比对删除，才精确回到基线 |
| B4 | 清理自己的后台任务时把服务连带杀掉 | API 进程随之消失，状态查询报「服务没有响应」 | 服务一度处于停止状态 |
| B5 | 误以为分离进程已经常驻 | 拉起后显示就绪，命令一结束进程即被回收，我却按「已就绪」继续往下走 | 中间多轮无效执行 |
| B6 | 本机 shell 调用系统命令的写法踩坑 | 反复失败两轮，报错与路径转换有关 | 浪费数轮工具调用，最终改用 Python 子进程方式 |

### 2.3 环境 / 能力限制（1 条）

| # | 说明 |
|---|---|
| C1 | 从本会话拉起的进程，命令结束时会被系统回收，**我无法提供「永久运行」的服务**。最终服务停止是这一限制的结果，不是没启动；数据全在数据库容器内，不受影响 |

### 2.4 上一轮已发现、本次复测确认仍在的遗留缺陷（4 条）

| # | 问题 | 状态 |
|---|---|---|
| D1 | 路由函数对非字符串输入（如数字）会崩溃，缺类型守卫 | 已知未修，本次未触发 |
| D2 | 语义路由方案实测劣化已停用，但文件仍在，成为死代码 | 未删 |
| D3 | 路由中某段分支判断永不可达（关键词表中不含该库） | 未修 |
| D4 | 交付文档声称「一键启动端到端实测通过」 | **本次被 A1 直接证伪** |

### 2.5 两条「看着像错、核实后不是」

- **召回耗时 0.0–0.3 秒且全部命中**：速度反常，怀疑是字段误匹配的假命中，逐条核了返回正文，确认返回的确实是含标记的真实记忆文本 → 真命中，不是问题。
- **`GET /banks/{id}` 返回 405**：不是服务坏了，是我用法错了（B2）。这条记在我头上。

**小结：本阶段共记录 11 条真实发生的问题（A3 + B6 + C1），另有 4 条历史遗留确认仍在。其中 A1 是唯一达到「交付不成立」级别的缺陷。**

## 三、原因分析：上一项任务是否「草率标记已完成」（阶段②）

### 3.1 核查结论

**是。存在未完成却被标记为「已完成/可交付」的情况。** 但不是全部，下面两边都列证据。

### 3.2 确实做成、本次复测有据的部分

| 声称 | 本次核验方式与结果 | 判定 |
|---|---|---|
| 四份模板改动已同步到线上库 | 逐库比对指令文本：聊天 4 / 编排 5 / 研究 4 / 平原 2，**未上线 0 条、线上多出 0 条** | 属实 |
| 交付时写入的真实记录仍在 | 四库数据条数与交付时一致 | 属实 |
| 「验收后清除测试数据」 | 按测试标签严格查询，四库残留均为 0；失败操作数为 0 | 属实 |
| 入口脚本可用 | 本次复测：状态查询、路由预演、噪声过滤、跨库切段全部正常 | 属实 |

### 3.3 没做完却标了「通过」的部分

| # | 声称 | 实际 | 判定 |
|---|---|---|---|
| 1 | 交付评估写「一键启动端到端实测通过」 | **从未做过一次冷启动验证**。服务自前日一直在跑，把它杀了才暴露崩溃 | 不成立 |
| 2 | 「四个库全部走通写入→检索」「六项阈值全绿」 | 用例与被测词表同源，且 300 条是 500 条的子集；换成全新措辞的独立测试集只有 84% | 结论不能成立 |
| 3 | 验收规范自称「已按接口实测字段修正」 | 其第 B.8 节的删除接口实测 405 不可用 → 那套规范自己也没跑过 | 不成立 |

### 3.4 四条根本原因

**R1｜环境依赖没有进入交付面（A1 的直接成因）**
证据链闭合：唯一带完整环境变量的历史脚本是前一天下午写的，而交付用的启动脚本是当夜 22:20 现写的，**两者之间没有任何继承**；用户级与机器级环境变量均为空，也没有配置文件。服务之所以一直在跑，是因为它早在环境变量正确的上下文里被拉起——**「服务在跑」被误当成了「启动路径验证过」**。

**R2｜自证式验收：测试集与实现同源**
500/300 条用例是按报错反过来补的词表，300 条又是 500 条的子集，查询词全部从用例原文抽词。这套结构**保证它必然全绿**。

**R3｜规范自己写、自己改、自己执行、自己判定**
没有第二双眼睛，也没做回滚路径预演（删除接口 405 就是证据）。

**R4｜收尾时间挤压 + 文档的选择性呈现**
全部交付物的时间戳落在 **22:20 → 22:34 的 14 分钟**内产出。更关键的是：同一份文档目录里，另一份自评报告白纸黑字写着「不能说这套记忆库可用了」，但最终交付结论是「可以交付、建议现在停」，**没有引用这个自评**。已知边界被留在了另一份文件里，没进结论。

### 3.5 具体遗漏的验证步骤

| 遗漏环节 | 应有的动作 | 后果 |
|---|---|---|
| 冷启动复验 | 杀掉服务，用常规方式双击启动脚本跑一遍 | A1 藏到本次才暴露 |
| 停→启往返 | 确认重启后配置、使命、指令仍在 | 未验证（本次已补做：指令 0 缺失） |
| 把独立测试集设为交付门槛 | 150 条全新用例应写进交付结论而非附录 | 84% 的真数字没成为判据 |
| 回滚 / 删除路径预演 | 先试删一条再来写规范 | 规范写了不存在的接口 |
| 边界条件输入 | 非字符串、超长、空值 | 路由崩溃至今未修 |

### 3.6 本次分析中新发现的缺口

四份模板文件的配置块**不含完整的服务端配置字段**（缺 `mission`，`disposition` 采用扁平命名），而线上库是 `mission` + 嵌套结构。**说明模板并非完整的配置源**，同步脚本内部做了一次隐式转换。

由此得出的判断：**「有模板就等于能重建四库」这个说法要打折**——真要把环境重建起来，光有模板目录不够，还缺环境变量与 bank 级字段。

## 五、给自己定下的四条红线

| # | 红线 |
|---|---|
| 1 | **判定某一功能可用之前，必须先做一次冷启动 / 冷路径验证**，不接受「它一直在跑所以是对的」 |
| 2 | **测试集必须与实现不同源**，否则不准用于证明结论 |
| 3 | **已知的负面自评必须出现在最终结论里**，不允许留在另一份文档中不被引用 |
| 4 | 任何会改变既有数据的操作，先停、先汇报、等确认，不先斩后奏 |
